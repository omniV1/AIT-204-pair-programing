System Architecture

The project follows a clear frontend/backend split. The Streamlit app (activity4_app.py) handles all user interaction and display; it never touches the model or vocabulary directly. Instead, it holds a single SentimentService instance (cached at startup) and calls predict(text) or compare(original, translated). The backend (model_service.py) loads the saved model and vocabulary once and exposes these two methods. Training and preprocessing live in Activity 1–3; at runtime only the saved artifacts and the service are used.

This separation allows swapping the UI (e.g. Streamlit for React) or the model without rewriting the other layer, and keeps the backend testable on its own (e.g. python model_service.py). Activity 1 — ML Pipeline: Preprocessing Module

File: activity1_preprocessing.py. Neural networks operate on numeric tensors, so raw text must be turned into fixed-size integer sequences. This module implements that pipeline and is used both during training (Activity 3) and at inference (via model_service.py when a user submits a review).

Pipeline Overview
From raw text to model input

First, text is normalized: clean_text() lowercases, strips non-letters, and collapses whitespace so that "This Movie was GREAT!!!" becomes "this movie was great". Then tokenize() splits on spaces into word tokens. The Vocabulary maps each token to an integer ID (unknown words map to <UNK>); pad_sequence() truncates or pads to a fixed max_length so every batch has the same shape. Finally, the list of integers is wrapped in a PyTorch tensor of shape (1, max_length) for the model. The flowchart below summarizes this sequence.

flowchart LR A[Raw Text] --> B[clean_text] B --> C[tokenize] C --> D[vocab.encode] D --> E[pad_sequence] E --> F["tensor(B, L)"]

Figure 2: Preprocessing pipeline from raw string to batched tensor.

Vocabulary and deployment
Word-to-ID mapping and persistence

The Vocabulary class is built from training data with build(token_lists) and respects a min_freq threshold so rare words fall back to <UNK>. It provides encode(tokens) and decode(indices) for the pipeline, and save(filepath) / Vocabulary.load(filepath) so the exact same mapping is used in the deployed app. Special tokens <PAD> (0) and <UNK> (1) are always present. The convenience function preprocess_for_model(text, vocab, max_length) runs the full chain for a single string; preprocess_dataset(reviews, vocab, max_length, fit_vocab=False) does batch preprocessing and can optionally build the vocabulary from the given reviews.

Activity 2 & 3 — Model Architecture and Training

Files: activity2_model.py defines the network; activity3_train.py trains it on IMDB and saves the model, vocabulary, and config.

SentimentClassifier

The model turns a sequence of word IDs into a single probability. An nn.Embedding layer looks up a dense vector for each ID; padding IDs are forced to zero via padding_idx. Those vectors are then averaged over the sequence (ignoring padding) to get one sentence vector per batch item. That vector passes through a fully connected block: Linear(embed_dim → hidden_dim), ReLU, Dropout, Linear(hidden_dim → 1), Sigmoid. So the architecture is: Word IDs → Embedding → Average Pooling → FC → ReLU → Dropout → FC → Sigmoid. It mirrors a Topic 2–style feed-forward net with an embedding layer at the front. save_model() and load_model() persist the config and state dict so the app can load the same architecture and weights.

flowchart LR subgraph model["SentimentClassifier"] I["(B, L) IDs"] I --> Emb[Embedding] Emb --> Pool["Avg Pool\n(mask pad)"] Pool --> FC1[Linear] FC1 --> R[ReLU] R --> D[Dropout] D --> FC2[Linear] FC2 --> S[Sigmoid] S --> O["(B, 1) prob"] end

Figure 4: Model data flow from token IDs to sentiment probability.

Training pipeline

Activity 3 loads the IMDB dataset (e.g. via Hugging Face datasets), builds the vocabulary from the training texts, and encodes and pads all sequences to MAX_LENGTH. It creates a SentimentClassifier with chosen hyperparameters (e.g. EMBED_DIM=128, HIDDEN_DIM=64, DROPOUT=0.5, MIN_FREQ=5), then runs a standard training loop: forward pass, BCE loss, backward, Adam step. Train and validation loss and accuracy are logged per epoch and plotted to plots/training_curves.png. After training, the script writes saved_model/model.pt, saved_model/vocab.json, and saved_model/config.json (containing max_length) for the app to load.

Activity 4 — Deployed Application (Backend and Frontend)

The app is split into a backend service and a Streamlit frontend. The backend owns the model and vocabulary; the frontend owns the UI and calls the backend. No model logic lives in the UI code.

Backend: SentimentService

On construction, SentimentService loads the vocabulary from vocab.json, the model from model.pt, and max_length from config.json. predict(text) runs the full preprocessing pipeline (clean, tokenize, encode, pad, tensor), passes the tensor through the model, and returns a dict with sentiment label, confidence, positive/negative scores, and pipeline intermediates (cleaned text, tokens, encoded IDs, known_count) for display. compare(original, translated) calls predict() on both strings, computes the score delta and whether the sentiment label flipped, and identifies vocabulary words that appear in one text but not the other (lost_words / new_words). Frontend: Streamlit

load_service() is decorated with @st.cache_resource so one SentimentService() is created and reused for the lifetime of the app; the model is not reloaded on every button click. Tab 1 (Sentiment Analysis) provides a text area and an "Analyze Sentiment" button that calls service.predict(review) and shows the sentiment, confidence, a positive-score progress bar, and an expander with cleaned text and tokens. Tab 2 (Translation Comparison) provides two text areas (original and round-trip translated); "Compare Sentiments" calls service.compare(original, translated) and shows both predictions, the score delta, whether the label changed, and lost/new words. Deployment (e.g. Streamlit Community Cloud or Hugging Face Spaces) requires the repo to include the app file, backend, Activity 1–2 modules, saved_model/, and requirements.txt, with the app file as the entry point.

Translation Analysis and Cross-Lingual Evaluation

A round-trip translation experiment was conducted using 10 diverse IMDb-style reviews. Each "Original" review was translated into a foreign language (Spanish, French, or Japanese) and then back to English using a neural translation model. These pairs were then compared using the SentimentService.compare() method to identify sentiment drift, label flips, and vocabulary loss.

Experiment #1: Descriptive Positive

Preserved
Linguistic Analysis

Original: "Adrian Pasdar is excellent is this film. He makes a fascinating woman."

Translated: "Adrian Pasdar is excellent in this film. He plays a fascinating woman."

Feature Identification: The translation corrected a grammatical error ("is" to "in") and replaced "makes" with "plays". Since "excellent" and "fascinating" were preserved, the model maintained a 1.000 confidence score.

Delta: 0.000 (No change)

Experiment #2: Strong Negative

Preserved
Linguistic Analysis

Original: "Long, boring, blasphemous. Never have I been so glad to see ending credits roll."

Translated: "Long, tedious, blasphemous. I've never been so happy to see the end credits roll."

Feature Identification: "Boring" shifted to "tedious" (synonym) and "glad" to "happy". While "happy" is usually positive, in the context of "ending credits", the strong negative embeddings for "blasphemous" and "tedious" dominate.

Delta: +0.118 (Slightly less negative)

Experiment #3: Sarcasm & Sentiment Flip

Label Flipped
Linguistic Analysis

Original: "I don't know why I like this movie so well, but I never get tired of watching it."

Translated: "I don't know why I like this movie so much, but I never get tired of watching it."

Feature Identification: CRITICAL ERROR. A minor semantic shift from "well" to "much" caused the model to flip from Positive (0.649) to Negative (0.037). This suggests the model relies heavily on specific word patterns rather than global context.

Delta: -0.612 (Extreme Shift)

Experiment #4: Aggressive Negative

Preserved
Linguistic Analysis

Original: "no comment - stupid movie, acting average or worse... screenplay - no sense at all... SKIP IT!"

Translated: "No comment - stupid movie, mediocre acting or worse... completely nonsensical script... STAY AWAY!"

Feature Identification: "Average" shifted to "mediocre" and "SKIP IT" to "STAY AWAY". Both pairs have strong negative associations in the training data, so the 0.000 score was perfectly preserved.

Delta: 0.000 (No change)

Experiment #5: High-Level Sarcasm

Preserved
Linguistic Analysis

Original: "This is the definitive movie version of Hamlet. Branagh cuts nothing, but there are no wasted moments."

Translated: "This is the definitive film version of Hamlet. Branagh cuts nothing, but there are no wasted moments."

Feature Identification: Paradoxically, the model rates this highly positive review as Negative (0.005). Translation changed "movie" to "film", but the sentiment remained identical. This highlights a limitation in the model's training on specific vocabulary.

Delta: +0.001 (Negligible)

Experiment #6: Actor/Director Focus

Preserved
Linguistic Analysis

Original: "The characters are unlikeable and the script is awful. It's a waste of the talents of Deneuve and Auteuil."

Translated: "The characters are unlikeable and the script is terrible. It's a waste of Deneuve and Auteuil's talent."

Feature Identification: "Awful" became "terrible". Since both are strong negative anchors in the vocabulary, the sentiment score remained at the minimum (0.000).

Delta: 0.000 (No change)

Experiment #7: Classic Cinema Hyperbole

Semantic Shift
Linguistic Analysis

Original: "This movie will always be a Broadway and Movie classic..."

Translated: "This film will always be a Broadway and cinematic classic..."

Feature Identification: The translation refined "Movie" to "cinematic". The model showed a slight drop in confidence (from 0.997 to 0.967), likely because "movie" (appearing twice in original) has a higher weight in the vocabulary than "cinematic".

Delta: -0.030 (Slightly less confident)

Experiment #8: Fan Feedback

Preserved
Linguistic Analysis

Original: "Unwatchable. You can't even make it past the first three minutes."

Translated: "Unwatchable. You can't even get past the first three minutes."

Feature Identification: "Make it past" to "get past". The word "Unwatchable" is such a strong negative token that minor grammatical variations in the rest of the sentence do not affect the output.

Delta: 0.000 (No change)

Experiment #9: Mixed Review Contrast

Contextual Loss
Linguistic Analysis

Original: "As usual, Sean Connery does a great job. Lawrence Fishburn is good..."

Translated: "As always, Sean Connery does a great job. Lawrence Fishburne is good..."

Feature Identification: "As usual" to "As always". The model increased confidence from 0.977 to 0.999. "Always" likely has a stronger positive weight correlation than "usual" in the training set.

Delta: +0.023 (Slightly more positive)

Experiment #10: Nuance Flip

Label Flipped
Linguistic Analysis

Original: "Malcolm McDowell has not had too many good movies lately and this is no different."

Translated: "Malcolm McDowell hasn't made many good films lately, and this one is no different."

Feature Identification: BOOM. The original was correctly identified as Negative (0.066). The translation flipped it to Positive (0.875). Replacing "had too many good movies" with "made many good films" triggered the "good" positive weight while losing the negative negation nuance.

Delta: +0.809 (Catastrophic Shift)

Ethical Considerations
Training Data
Bias in Training Data

The sentiment analysis model is trained on the IMDb movie review dataset, meaning its understanding of "positive" and "negative" sentiment is inherently biased towards the linguistic patterns, cultural norms, and demographics of IMDb reviewers. This can lead to misclassification of reviews written in different dialects, socio-economic contexts, or cultural frameworks, inadvertently silencing or misrepresenting certain groups.

Data Security
Privacy of User-Generated Text

Processing user-generated text requires stringent privacy controls. When users input text into the application, they may inadvertently include personally identifiable information (PII) or sensitive personal data. If this data is logged, stored, or used for further model training without explicit consent and robust anonymization, it violates user privacy and risks exposing individuals to harm.

Systemic Impact
Risks of Sentiment Analysis at Scale

Deploying sentiment analysis at scale can amplify the impact of model errors. If organizations rely on automated sentiment scores for decision-making (e.g., customer service triage, product development, or content moderation), the model's biases can systematically disadvantage certain users. The lack of human nuance can lead to tone-deaf responses, exacerbating customer frustration and damaging brand trust.

Translation Nuance
Cross-Lingual Harm from Translation Errors

As demonstrated in the translation analysis, neural translation models can introduce semantic shifts or lose contextual nuance. When sentiment analysis relies on translated text, these errors can completely flip the meaning of a statement (e.g., classifying a culturally specific positive idiom as negative). In critical applications, this cross-lingual misunderstanding can alienate non-native speakers or misinterpret international sentiment.

Accountability
Engineering Responsibility

Engineers bear the responsibility of recognizing and mitigating these ethical risks. This involves transparently documenting model limitations (as done in this report), implementing safeguards against PII ingestion, regularly auditing models for bias, and ensuring that automated systems remain tools to assist—rather than replace—human judgment. Responsible AI engineering requires a commitment to fairness, accountability, and continuous evaluation of real-world impact.

System Architecture

The project follows a clear frontend/backend split. The Streamlit app (activity4_app.py) handles all user interaction and display; it never touches the model or vocabulary directly. Instead, it holds a single SentimentService instance (cached at startup) and calls predict(text) or compare(original, translated). The backend (model_service.py) loads the saved model and vocabulary once and exposes these two methods. Training and preprocessing live in Activity 1–3; at runtime only the saved artifacts and the service are used.

This separation allows swapping the UI (e.g. Streamlit for React) or the model without rewriting the other layer, and keeps the backend testable on its own (e.g. python model_service.py). Activity 1 — ML Pipeline: Preprocessing Module

File: activity1_preprocessing.py. Neural networks operate on numeric tensors, so raw text must be turned into fixed-size integer sequences. This module implements that pipeline and is used both during training (Activity 3) and at inference (via model_service.py when a user submits a review).

Pipeline Overview
From raw text to model input

First, text is normalized: clean_text() lowercases, strips non-letters, and collapses whitespace so that "This Movie was GREAT!!!" becomes "this movie was great". Then tokenize() splits on spaces into word tokens. The Vocabulary maps each token to an integer ID (unknown words map to <UNK>); pad_sequence() truncates or pads to a fixed max_length so every batch has the same shape. Finally, the list of integers is wrapped in a PyTorch tensor of shape (1, max_length) for the model. The flowchart below summarizes this sequence.

flowchart LR A[Raw Text] --> B[clean_text] B --> C[tokenize] C --> D[vocab.encode] D --> E[pad_sequence] E --> F["tensor(B, L)"]

Figure 2: Preprocessing pipeline from raw string to batched tensor.

Vocabulary and deployment
Word-to-ID mapping and persistence

The Vocabulary class is built from training data with build(token_lists) and respects a min_freq threshold so rare words fall back to <UNK>. It provides encode(tokens) and decode(indices) for the pipeline, and save(filepath) / Vocabulary.load(filepath) so the exact same mapping is used in the deployed app. Special tokens <PAD> (0) and <UNK> (1) are always present. The convenience function preprocess_for_model(text, vocab, max_length) runs the full chain for a single string; preprocess_dataset(reviews, vocab, max_length, fit_vocab=False) does batch preprocessing and can optionally build the vocabulary from the given reviews.

Activity 2 & 3 — Model Architecture and Training

Files: activity2_model.py defines the network; activity3_train.py trains it on IMDB and saves the model, vocabulary, and config.

SentimentClassifier

The model turns a sequence of word IDs into a single probability. An nn.Embedding layer looks up a dense vector for each ID; padding IDs are forced to zero via padding_idx. Those vectors are then averaged over the sequence (ignoring padding) to get one sentence vector per batch item. That vector passes through a fully connected block: Linear(embed_dim → hidden_dim), ReLU, Dropout, Linear(hidden_dim → 1), Sigmoid. So the architecture is: Word IDs → Embedding → Average Pooling → FC → ReLU → Dropout → FC → Sigmoid. It mirrors a Topic 2–style feed-forward net with an embedding layer at the front. save_model() and load_model() persist the config and state dict so the app can load the same architecture and weights.

flowchart LR subgraph model["SentimentClassifier"] I["(B, L) IDs"] I --> Emb[Embedding] Emb --> Pool["Avg Pool\n(mask pad)"] Pool --> FC1[Linear] FC1 --> R[ReLU] R --> D[Dropout] D --> FC2[Linear] FC2 --> S[Sigmoid] S --> O["(B, 1) prob"] end

Figure 4: Model data flow from token IDs to sentiment probability.

Training pipeline

Activity 3 loads the IMDB dataset (e.g. via Hugging Face datasets), builds the vocabulary from the training texts, and encodes and pads all sequences to MAX_LENGTH. It creates a SentimentClassifier with chosen hyperparameters (e.g. EMBED_DIM=128, HIDDEN_DIM=64, DROPOUT=0.5, MIN_FREQ=5), then runs a standard training loop: forward pass, BCE loss, backward, Adam step. Train and validation loss and accuracy are logged per epoch and plotted to plots/training_curves.png. After training, the script writes saved_model/model.pt, saved_model/vocab.json, and saved_model/config.json (containing max_length) for the app to load.

Activity 4 — Deployed Application (Backend and Frontend)

The app is split into a backend service and a Streamlit frontend. The backend owns the model and vocabulary; the frontend owns the UI and calls the backend. No model logic lives in the UI code.

Backend: SentimentService

On construction, SentimentService loads the vocabulary from vocab.json, the model from model.pt, and max_length from config.json. predict(text) runs the full preprocessing pipeline (clean, tokenize, encode, pad, tensor), passes the tensor through the model, and returns a dict with sentiment label, confidence, positive/negative scores, and pipeline intermediates (cleaned text, tokens, encoded IDs, known_count) for display. compare(original, translated) calls predict() on both strings, computes the score delta and whether the sentiment label flipped, and identifies vocabulary words that appear in one text but not the other (lost_words / new_words). Frontend: Streamlit

load_service() is decorated with @st.cache_resource so one SentimentService() is created and reused for the lifetime of the app; the model is not reloaded on every button click. Tab 1 (Sentiment Analysis) provides a text area and an "Analyze Sentiment" button that calls service.predict(review) and shows the sentiment, confidence, a positive-score progress bar, and an expander with cleaned text and tokens. Tab 2 (Translation Comparison) provides two text areas (original and round-trip translated); "Compare Sentiments" calls service.compare(original, translated) and shows both predictions, the score delta, whether the label changed, and lost/new words. Deployment (e.g. Streamlit Community Cloud or Hugging Face Spaces) requires the repo to include the app file, backend, Activity 1–2 modules, saved_model/, and requirements.txt, with the app file as the entry point.

Translation Analysis and Cross-Lingual Evaluation

The rubric asks for a round-trip translation experiment (at least 10 examples), model-based comparison of original vs. translated sentiment, and classification of translation effects (e.g. grammatical error, semantic shift, contextual loss, or preserved meaning).

Round-trip means taking an English review, translating it to another language (e.g. with Google Translate or DeepL), then translating back to English. The original and the round-trip text are pasted into the Translation Comparison tab; compare() returns both sentiment scores, the delta, a boolean changed (true if the label flipped), and the sets of vocabulary words that were lost or introduced. In the written report, each example should be classified (grammatical, semantic, contextual, or preserved) and documented with the model outputs. The decision tree below summarizes how the app and report interpret "sentiment changed" and how to use the outputs for analysis.
